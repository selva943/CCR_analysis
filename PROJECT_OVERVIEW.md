# CCR_analysis — Project Overview (for ChatGPT / LLM onboarding)

This document explains what this project is, how it is built, what the data looks
like, and — most importantly — **what analyses have been implemented** and how each
one is calculated. Read this first, then dive into `dashboard/js/*.js` for the
actual code.

---

## 1. What the project is

A **standalone, client-side DSE field-force analytics dashboard** for MTD (Month-To-Date)
**CCR** (call-logging) data. It analyses the day-to-day activity of **DSEs**
(Distribution Sales Executives) — store visits, working discipline, productivity,
store time, geographic route adherence, risk and data quality.

Key properties:

- **100 % browser-side.** No backend, no server. All computation happens in the browser's JS engine.
- **Works offline.** The distribution file (`output/MTD_CCR_Dashboard.html`) embeds the entire
  XLSX workbook (compressed) plus all CSS/JS/vendor libraries. Open it with `file://` and it runs.
- **Source of truth** is the folder `dashboard/`. Build scripts regenerate the deployable copies.

### The two flavours of the app

| Flavour | Location | How it loads data |
|---|---|---|
| Dev / source | `dashboard/` (`index.html` + `js/`, `css/`, `vendor/`) | Fetches `Input/MTD_CCR.xlsx` over HTTP, or prompts for a file |
| Standalone / distribution | `output/MTD_CCR_Dashboard.html` | Data embedded inside the HTML, loads instantly with no server |
| Netlify deploy | `dist/` | Static copy of `dashboard/` served by Netlify |

## 2. Data model

### Source workbook

`Input/MTD_CCR.xlsx`, first sheet, ~85,071 rows (≈80,055 pass validation).

Columns the app needs (headers are matched case-insensitively / by normalised key):

`DSE code, DSE name, date, branch code, branch location, ZSM, ASM, ASO, route name,
retailer code / name, channel name, sub channel name, in-market status, day start time,
start time, end time, intime, duration, distance travelled, order value, calls made,
call compliance, below 5 mins, reason, deviation in meter, deviation flag, reason for
deviation, on route, productivity, visit latitude, visit longitude, remarks,
visit p1m / p3m / ipdp achievement, contact numbers.`

### Normalisation performed on load (`data.js: processSheet`)

Every raw row is normalised into a `visit` object:

- Dates → ISO `YYYY-MM-DD`; times → **minutes from midnight** (`toTimeMinutes`).
- `on_route` and `productivity` → `YES` / `NO` / `UNKNOWN`.
- `call_compliance` → `YES` (numeric ≥ 1 also counts as YES) / `NO` / null.
- `channel_name` → normalised channel class (`SMALL` / `WS` / `LARGE` / `SELF SERVICE` /
  `SPECIALITY`). **SPECIALITY is excluded from channel-level and store-time logic.**
- Latitude/longitude validated against a sensible India bounding box; `(0,0)` rejected.

### Cleaning / rejection rules (rows are never silently used)

A row is rejected (and counted in the **Data Quality** report) when any of these is true:

- Missing/unparseable date, DSE, start time or end time
- Negative duration (end < start)
- Missing/invalid coordinates (outside bounds or `0,0`)
- Null or negative deviation
- `on_route` / `productivity` unparseable (`UNKNOWN`)
- Duplicate row (duplicate key = DSE + date + retailer; or exact same visit times)
- Missing `intime` (counted, flagged if >5 % of rows)

## 3. Analytics layers (the analyses we did)

The pipeline runs `<load> → clean → build daily → build DSE → risk → ranking
→ insights`, then renders the active module.

### 3.1 Daily aggregation — `metrics.js: buildDaily` (per DSE × date)

For each DSE-day, computed from its visits:

- **Start pass** = day's *first store-visit start time* ≤ 09:30 (falls back to the
  reported `day_start_time` only if no visit has a start time).
- **On-route rate** = on-route `YES` ÷ visits with a known route.
- **Deviation rate** = deviation ≤ 100 m ÷ visits with a deviation.
- **Productivity %** = (on-route `YES` **and** productive `YES`) ÷ on-route `YES`.
- **Working minutes** = last visit end − first visit start (cap 18 h).
- **Store time** = sum of visit `end − start`; per-DSE-day **median** is kept.
- **Day discipline score** = weighted blend of start / route / deviation (see 3.2).

### 3.2 Discipline score (0–100, per DSE)

```
disciplineScore = startWeight × start%  +  routeWeight × on-route%  +  devWeight × deviation%
```
Default weights **(editable)**: Start **40 %** · On-route **30 %** · Deviation **30 %**.

Classification: **GOOD ≥ 80**, **MODERATE 60–80**, **RISK < 60**.
*Strict compliant* = 100 % on all three conditions on every worked day.

### 3.3 Productivity (%)

```
productivity% = (ON ROUTE = YES AND PRODUCTIVITY = YES) ÷ (ON ROUTE = YES) × 100
```
Deliberately kept separate from call compliance, productive calls and total calls.

Other day-level metrics: call compliance %, call count, below-5-min calls,
order value, avg/max deviation.

### 3.4 Working hours & store time

- **Working hours** = first-visit start → last-visit end per day (max 18 h), averaged
  over worked days. Default target **7 h (420 min)**.
- **Store time** = per-visit `end − start`, aggregated as a DSE-day median; store
  visits > 240 min are excluded from the box plot (noted as `longDurations` in Quality).

### 3.5 Risk score (per DSE, 100-point sum)

Independent weighted flags (`metrics.js: computeRisk`):

| Flag | Weight | Trigger |
|---|---|---|
| Late Start | 20 | on-time start % < 75 % |
| Off Route | 20 | on-route % < 90 % |
| High Deviation | 20 | deviation-compliant % < 90 % |
| Low Productivity | 20 | productivity < team median |
| Low Work Hours | 10 | avg working < 7 h |
| Low Call Compliance | 10 | call compliance < 80 % |
| Excess Store Time | 10 | avg store time > 1.5 × team median |
| Low Order Value | 10 | avg order < 0.5 × team median |

Class: **LOW ≤ 20 · MODERATE 21–40 · HIGH 41–60 · CRITICAL 61+**.

### 3.6 Overall ranking score

```
prodScore = min(100, productivity% ÷ maxTeamProductivity × 100)
effScore  = min(100, productive-calls-per-store-hour ÷ team max × 100)
Overall   = 40 % × disciplineScore + 35 % × prodScore + 25 % × effScore
```
Used to rank DSEs and colour calendars / matrices.

### 3.7 Insights engine — `insights.js: generate` (deterministic, rule-based)

Produces a structured list: `summary, positive, risk, anomaly, opportunity, action`.
What it computes:

- **Team snapshot** — counts of late starters (<75 % on-time), off-route (<90 % route
  adherence), high-deviation, sub-7-hour DSEs.
- **Best all-round performer**, **highest converter** (≥60 % productivity, ≥5 visits),
  **efficient workers** (≥60 % productivity in <7 h).
- **Risks** — late-start, route adherence, deviations, <30 % converters (severity scales
  with how many DSEs are affected).
- **Anomalies** — *group comparison*: on-time vs late starters (productivity & calls/day),
  7+ h vs <7 h DSEs; conclusion is phrased automatically from the data.
- **Opportunities** — channel time-share analysis (which channel eats store time vs its
  conversion), "long hours but low conversion" DSEs, and efficiency champions.
- **Actions** — immediate intervention list (CRITICAL + HIGH risk DSEs, flag reasons).

### 3.8 Channel analysis

For the 4 main channels: store-time share, visits, productivity %, avg per-store time.
Used in Store Time module and the channel insight above.

## 4. Modules (what each tab renders) — `ui.js`

Navigation in `index.html`. `app.js: setActiveSection()` switches modules and **closes
the filter dropdown**. `app.js: render()` dispatches to each renderer.

### ◧ Executive (`renderExec`, `renderManagementSummary`)
- Management summary: team discipline %, productivity %, avg hours, on-route %, DSEs at
  risk, best performer, auto-picked "most pressing concern".
- KPI grid: DSE counts, discipline classes, productivity %, hours share, compliance,
  calls/store/working totals.
- **Discipline trend** & **Productivity trend** (ECharts lines, daily).
- **DSE performance matrix** — scatter: start time (x) vs avg deviation (y), bubble =
  call volume, colour = discipline class, threshold lines at 09:30 / 100 m.
- **Discipline distribution** (donut), **team scorecard** (target benchmarks).
- Efficiency scatters: working hours vs productivity, store time vs productivity.
- **Overall ranking table** (sortable; click row → DSE profile).

### ◈ Discipline (`renderDiscipline`)
- KPIs: overall/start/route/deviation discipline, Good/Moderate/Risk, strict compliant.
- **Discipline trend** (multi-line, daily/weekly): start, route, deviation, discipline.
- **Start-time distribution** histogram; **deviation distribution** (log scale).
- **Discipline matrix** (start vs deviation scatter).
- **Daily discipline area chart** — daily "hit count": for each DSE-day only the first
  store visit is checked (On route = YES AND dev ≤ 100 m AND start ≤ 09:30); one hit
  max per DSE-day, integer Y-axis.
- Per-DSE matrix and **calendar heatmap** (small teams).

### ◉ Productivity (`renderProductivity`)
- KPIs: productivity %, numerator/denominator, call counts, 7+ h / <7 h DSEs, call compliance.
- Productivity trend; grouped bars: on-time vs late start, 7+ h vs <7 h.
- Scatter: productivity vs working hours (bubble = order value).
- **Productivity quadrant** — split by 7 h and team-median productivity into
  **Star / Efficient / Hard-worker / Risk**.
- Productivity ranking table (click → DSE profile).

### ◔ Store Time / Spend (`renderSpend`)
- **Store time by channel** (stacked bars, top-30 DSEs; toggle Hours / % / Visits / Avg min).
- **Channel time share** (donut).
- **Store-time distribution** (Plotly box plots per channel).
- **Store time vs productivity** (scatter).
- Channel performance table + store-efficiency ranking (productive calls per store hour).

### ✜ Geography (`renderGeo`, `initGeoMap`, Leaflet)
- KPI grid: geo-coded visits, DSEs mapped, on-route/off-route/high-deviation counts.
- **Interactive visit map** — Leaflet circle markers (size by radius, colour by
  type: red = high deviation, amber = off route, green = productive, blue = other),
  with layer toggles (On-route / Off-route / High-deviation / Productive).
- The map uses the **global filters** (set via the Filters button); there is **no
  separate geo filter panel**. Map is drawn only after clicking **Load map**.
- **Click a marker** → DSE profile modal with a sequenced **movement trace map**
  (`renderMovementMap`) for a chosen day + per-visit log + CSV export.

### ⚠ Risk & Insights (`renderRisk`)
- **Risk radar** (top-5 risk DSEs across the 8 risk components).
- **Deterministic AI insight blocks** from section 3.7.
- **Management action table** — DSE × issue × evidence × severity × recommended action.

### ◪ Data Quality (`renderQuality`)
- Rejection-class counts (duplicates, missing date/DSE/times/coordinates, invalid
  deviation/productivity, negative duration, long durations, missing channel/order,
  etc.) with pass/fail colouring.
- Rejected-rows detail table.

## 5. Filters (shared across modules)

A single global filter bar (dropdown opened from the **Filters** button, id
`#filterbar`). All filters combine with **AND** logic. Changing any filter triggers
`compute()` → full re-analysis → re-render; switching modules closes the dropdown.

- Date from / to (inclusive, ISO)
- Branch location, ZSM, ASM, ASO (management hierarchy)
- DSE (multi-select)
- Channel
- On route (All / Yes / No)
- Deviation flag / etc. via the shared pickers

`app.js: compute()`:
`read global filters → filterVisits → buildAll (daily + DSE list + benchmarks) →
computeRisk → computeRanking → discipline → render current module`.

## 7. Technology / libraries

Vanilla JS (IIFE modules sharing a `window.DSE` namespace), no bundler.

- **SheetJS (xlsx.full.min.js)** — workbook parsing.
- **PapaParse** — CSV export.
- **ECharts** — most line/bar/pie/radar/heatmap charts.
- **Plotly** — box plots (store-time distribution).
- **Leaflet** (OpenStreetMap tiles) — geography maps.
- **Node.js** — only for the offline build scripts.

### Why the standalone build is fast
`data.js` encodes visits as **columnar, dictionary-encoded, gzip + base64** JSON
(`encodeVisitsCompact`), ~10× smaller than raw base64 XLSX, so the single HTML loads
85k rows instantly without re-parsing the workbook.

## 9. Recent changes worth knowing (so an LLM doesn't regress them)

- The Geography module previously had its **own inline filter panel**
  (`.geo-filters`, single-select, bound to a `state.geoFilters` clone). It was
  removed — the map now uses the **global filterbar** filters only.
  Related dead code was deleted: `readGeoFilters`, `gOpts`, `state.geoFilters`,
  and the `.geo-filters` CSS rules.
- The global filter dropdown now **auto-closes** whenever the user switches modules
  (`app.js: setActiveSection`).
- **Risk & Insights has a hierarchy drill-down** (`ui.js: renderDrillPanel`). At the
  top of the module there is a breadcrumb + card grid that drills
  `Overall → ZSM → ASM → ASO → DSE`. State lives in `state.drill`
  (`{zsm, asm, aso}`), mutated via `state.setDrill()`. `ui.js: buildScope()` clones the
  DSE stats for the drilled group and recomputes team/risk/ranking so all insight
  cards ("Needs attention", "Ways to improve", "Who needs support", radar, action
  list) are scoped to that node. Scoped engine results are cached in
  `state._drillEngineCache` keyed by `zsm|asm|aso`. Changing global filters resets a
  drill only if the drilled entity no longer exists (`app.js: compute()`).
- `insightEngine.js: aggregateHierarchy` now also aggregates an **ASO** level
  (`h.asos`) alongside `asms/zsms/branches`, and its group `productivity` is the real
  mean of DSE productivity percentages (previously it was accidentally ×100, which
  also broke the ASM/ZSM hierarchy insight gap comparisons).
